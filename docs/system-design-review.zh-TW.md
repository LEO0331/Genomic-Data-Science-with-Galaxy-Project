# 系統設計評審（繁體中文）

## 1. 範圍與產品邊界

本系統是基於 Galaxy 變異分析結果的**展示與探索層**。

系統刻意**不**在網頁端執行 FASTQ/BAM 的原始高運算流程。

### 範圍內
- 流程可視化與敘事
- 瀏覽器端 VCF 解析與篩選
- 成果檔案下載
- 輕量 API（健康檢查與變異摘要）

### 範圍外
- 分散式基因體運算排程
- 多租戶帳號/權限治理
- 臨床等級合規資料平台

---

## 2. 高階架構

```mermaid
flowchart LR
  U[使用者瀏覽器] --> N[Next.js App Router 前端]
  N --> P[Public 檔案 /public/*.vcf *.ga *.pdf]
  N --> V[前端 VCF 解析 lib/vcf.ts]
  N --> A1[/api/health]
  N --> A2[/api/variants/summary]
  A2 --> V
  CI[GitHub Actions] --> QA[Lint + Typecheck + Coverage + E2E + Lighthouse]
  QA --> D[部署至 Vercel]
```

### 核心設計選擇
- **主要資料路徑採用前端解析**，以降低維運成本並提升互動回饋速度。
- 後端 API 保持最小化與無狀態。

---

## 3. 主要元件與責任

1. `app/*` 路由
- 頁面組裝、導覽與內容呈現。

2. `components/*`
- 可重用視覺元件（時間軸、表格、卡片、上傳器等）。

3. `lib/vcf.ts`
- VCF 解析、篩選、摘要、CSV 匯出核心邏輯。
- 前後端共用，避免規則漂移。

4. `app/api/*`
- `/api/health`：服務存活檢查。
- `/api/variants/summary`：輸入驗證與摘要計算。

5. CI/CD
- 品質閘道與自動部署流程。

## 4. 資料結構選型：為何這樣選

## 4.1 `VariantRecord[]`（型別化陣列）

選擇原因：
- VCF 天然是列資料（row-based）。
- UI 表格與篩選邏輯直接對應。
- 實作簡潔、維護成本低。

替代方案：
- `Map<string, VariantRecord[]>`（以染色體分桶）
  - 重複染色體查詢較快，但跨欄位全文篩選更複雜。
- 欄式儲存（columnar）
  - 大規模分析較佳，但前端可讀性與開發體驗較差。

取捨：
- 目前以中小型檔案為主，O(n) 線性掃描可接受。

## 4.2 `Set<string>`（唯一染色體統計）

選擇原因：
- 插入平均 O(1)，語意清楚。

替代方案：
- `Record<string, boolean>`
  - 功能可行，但語意不如 `Set` 直接。

## 4.3 手寫 CSV 字串組裝

選擇原因：
- 零額外依賴，降低供應鏈風險。
- 對目前資料量效能足夠且可測。

替代方案：
- CSV 套件/串流匯出器
  - 邊界情況支援更完整，但增加依賴與維運成本。

## 4.4 `WorkflowStep[]` 靜態流程定義

選擇原因：
- 內容固定、可預期、無執行期外部依賴。

替代方案：
- CMS 或遠端 JSON
  - 非工程人員可編輯較方便，但引入額外可用性風險。

## 5. 架構取捨

## 5.1 以前端解析為主

優點：
- 本機上傳資料可留在瀏覽器內處理。
- 後端成本低、可擴展路徑簡單。

缺點：
- 大檔案受限於瀏覽器記憶體與 CPU。

緩解：
- 檔案大小上限（目前 10 MB）。
- 明確錯誤訊息與失敗路徑。

## 5.2 極簡後端

優點：
- 攻擊面較小。
- 維運複雜度低。

缺點：
- 伺服器端統計與查詢能力有限。

緩解：
- 保留 `/api/variants/summary` 作為未來擴充節點。

## 5.3 嚴格 CI 品質閘道

優點：
- 降低回歸風險，提升可交付品質。

缺點：
- Pipeline 時間較長、瀏覽器測試可能偶發不穩。

緩解：
- 測試保持聚焦與可重現。

## 6. 深入面試問題（Deep Dive）與答題重點

## Q1. 為何不直接上資料庫？
A：
- 當前產品目標是案例展示與互動探索，不是多租戶查詢平台。
- 若需求轉向協作、持久化、跨案分析，再引入資料庫是合理下一步。

## Q2. 大型 VCF 如何擴展？
A：
- 目前定位中小型互動檔案。
- 後續可加：分塊解析、Web Worker、伺服器端彙總 API、索引儲存。

## Q3. 為何同時保留前端與 API 摘要路徑？
A：
- 前端路徑滿足本機隱私與快速互動。
- API 路徑保留後端擴充能力。
- 共用 `lib/vcf.ts` 確保規則一致。

## Q4. 可靠性關鍵控制點是什麼？
A：
- 型別化邏輯、錯誤狀態處理、覆蓋率門檻、E2E 與 Lighthouse 閘道。

## Q5. 現在的安全邊界？
A：
- 無高敏感授權流程；API 有輸入與大小限制；CI 有依賴掃描與安全 header。

## Q6. 若升級到臨床等級，優先改什麼？
A：
- 合規治理、權限模型、審計軌跡、加密與資料處理邊界先到位。

---

## 7. 風險與演進路線

現階段風險：
- 超大檔案效能上限。
- 產品使用觀測能力有限。

演進建議：
1. 加入 Web Worker 解析路徑。
2. 增加可選後端摘要/索引服務。
3. 建立可持久化的 artifact metadata 層。
4. 若擴展協作場景，再加入 RBAC 與審計紀錄。
